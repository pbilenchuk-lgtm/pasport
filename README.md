# Монитор электронной очереди — паспортный сервис, Варшава

Следит за страницей [warszawa.pasport.org.ua/solutions/e-queue](https://warszawa.pasport.org.ua/solutions/e-queue)
и присылает в Telegram сообщение, как только появляются свободные даты для записи.

Записываться сам **не умеет и не будет** — только уведомляет. Запись руками.

## Разведка: что выяснилось из HAR

Это результат Этапа 0 из ТЗ. Читать обязательно — от этого зависит, почему код
устроен именно так.

### 1. Отдельного API со списком дат нет

В HAR-файле (60 запросов) **нет ни одного XHR/fetch с JSON-ответом** про даты или
слоты. Все запросы к домену — это сама страница, JS-чанки, шрифты, иконки и
телеметрия (Google Analytics, Cloudflare RUM).

Состояние очереди приходит **уже отрисованным в HTML** самой страницы. Когда мест
нет, в левой колонке лежит серверный блок:

```html
<div class="... border-red-500 bg-red-50 text-red-600" role="alert">
  <p><strong>Наразі всі місця зайняті.</strong></p>
  <p>Будь ласка, спробуйте в інший час або день.</p>
  <p>Кількість талонів обмежена пропускною здатністю центру.</p>
</div>
```

Это хорошая новость: чтобы узнать состояние, достаточно скачать одну HTML-страницу.
Никаких токенов, id услуги и офиса, тел запроса — ничего этого нет.

Виджет записи (выбор услуги, даты, верификация через Дію/BankID) — это ленивые
webpack-чанки `app.m-queue-*.js`, которые подгружаются только когда талоны есть.
На момент экспорта HAR мест не было, поэтому **разметку «открытого» состояния снять
не удалось**. Как парсер это компенсирует — ниже.

### 2. Cookies не нужны

У запроса страницы в HAR **нет заголовка `cookie` вообще**. Сессия не нужна,
CSRF-токенов нет, ничего не «протухает». Пункт ТЗ про перевыпуск cookies
неприменим — перевыпускать нечего.

### 3. Cloudflare блокирует по IP, а не по «роботности»

Ключевой момент. Проверено с датацентрового IP:

| Запрос | Результат |
|---|---|
| `curl` без заголовков | `403 Blocked for security reasons` (28 байт) |
| `curl` с полным набором браузерных заголовков из HAR | тот же `403` |
| TLS-отпечаток Safari (curl_cffi) | тот же `403` |
| Ваш браузер (`cf-ray: ...-PRG`, Прага) | `200 OK` |
| Тестовая машина (`cf-ray: ...-IAD`, датацентр США) | `403` |

В ответе **нет заголовка `cf-mitigated`** и нет HTML с JS-челленджем — значит это
не «Managed Challenge», который решается браузером, а **кастомное WAF-правило,
режущее по IP/ASN**.

Практический вывод, важный для деплоя:

> **Headless-браузер сам по себе эту блокировку не обходит.** Вариант Б из ТЗ
> помогает против JS-челленджей, а здесь блок другого рода. Решает не браузер,
> а «чистый» IP-адрес.

Поэтому в коде есть `SCRAPE_PROXY` — единственная настройка, которая реально
чинит ситуацию, если IP хостинга забанен. См. раздел
[«Если Cloudflare блокирует»](#если-cloudflare-блокирует).

## Как устроено

```
monitor.py     — основной цикл, логика уведомлений, CLI
fetcher.py     — загрузка страницы: прямой HTTP (Вариант А) или Playwright (Вариант Б)
parser.py      — разбор HTML в состояние очереди
proxies.py     — список прокси, ротация, разбор форматов
display.py     — виртуальный дисплей Xvfb для headful-браузера
notifier.py    — Telegram
state.py       — сохранение состояния между проверками
config.py      — все настройки из переменных окружения
tests/         — тесты + фикстуры реальной страницы
```

### Логика парсера

Разметку «даты есть» вживую снять не удалось, поэтому парсер намеренно
консервативен и различает **три** состояния, а не два:

| Что нашли на странице | Состояние | Действие |
|---|---|---|
| Маркер «Наразі всі місця зайняті» | `closed` | молчим |
| Маркера нет, есть виджет записи и/или даты | `open` | **шлём уведомление** |
| Ни того, ни другого | `unknown` | молчим, пишем в лог |

Так изменение вёрстки приведёт к «промолчали», а не к ложной тревоге в три часа
ночи. Если `unknown` держится ~час подряд (60 проверок), придёт отдельное
сообщение «возможно, изменилась вёрстка» — чтобы молчание не осталось незамеченным.

Даты извлекаются в форматах `12.08.2026`, `2026-08-12`, `03.11` и `14 серпня`,
приводятся к `ДД.ММ` и отдаются в порядке появления на странице.

### Кто прислал сообщение

К одному боту можно подключить несколько копий монитора — например, домашний
компьютер и сервер. Чтобы не гадать, откуда пришло сообщение и какую копию
чинить, каждое подписывается отдельной строкой:

```
🟢 Появились даты: 12.08, 13.08
Беги записываться: https://warszawa.pasport.org.ua/solutions/e-queue

🖥 PETRO-PC
```

Подпись определяется сама: на хостинге — `☁️` с названием сервиса, на своём
компьютере — `🖥` с его именем. Если хочется понятнее, задайте `INSTANCE_NAME`,
например `INSTANCE_NAME=домашний ноутбук`.

### Когда приходят уведомления

* **🚀 Монитор запущен** — при старте, со сводкой текущего состояния
  («сейчас мест нет»). Это же и самопроверка доставки. Беззвучно.
  Чаще раза в `STARTUP_NOTICE_COOLDOWN_MINUTES` не повторяется: перезапуски
  идут пачками, и без этого ограничения чат заполняется одинаковыми
  сообщениями. На уведомления о датах ограничение не влияет.
* **🟢 Появились даты** — при появлении дат, которых раньше не было, или при
  переходе очереди из закрытой в открытую. Со звуком.
  Повторно теми же датами не спамит.
* **✅ Сердцебиение** — раз в сутки в 10:00 (Europe/Warsaw): сколько было проверок
  и ошибок за сутки. Беззвучно.
* **⚠️ Забанили / сайт лёг** — после 5 ошибок подряд, затем пауза 15 минут.
  Присылается один раз за «эпизод», не на каждой пятой ошибке.
* **✅ Связь восстановилась** — когда сайт снова отвечает. Беззвучно.
* **🔴 Места закончились** — выключено по умолчанию, включается `NOTIFY_ON_CLOSE=true`.

## Запуск на своём компьютере (Windows)

Самый надёжный способ: домашний IP **не забанен**, в отличие от датацентровых.
Cloudflare показывает ему обычную проверку, и настоящий браузер её проходит.
Прокси при этом не нужны совсем.

> Проверка Cloudflare стоит и на домашнем IP тоже: `--probe` с обычным
> HTTP-клиентом покажет `ЧЕЛЛЕНДЖ/КАПЧА`. Это не бан и не поломка — просто
> обычный HTTP-клиент такую проверку пройти не может в принципе. Поэтому
> установщик ставит браузер и работает через него.

1. Установить [Python 3.10+](https://www.python.org/downloads/). Подходит и
   классический установщик (там нужна галочка **«Add Python to PATH»**), и
   новый Python install manager — `setup.bat` понимает оба.
   **После установки закрыть все открытые окна консоли**: PATH меняется только
   для новых окон.
2. Открыть чат со своим ботом в Telegram и нажать **`/start`**.
   Без этого Telegram не даст боту написать первым.
3. Скачать репозиторий, **распаковать архив** (запускать из ZIP нельзя) и
   открыть **`windows\setup.bat`** двойным щелчком.

Ничего компилировать не нужно: базовые зависимости — пакеты на чистом Python,
они ставятся на любой версии, включая самые свежие.

Скрипт всё сделает сам: создаст окружение, поставит зависимости и браузер
(около 150 МБ), спросит токен и chat_id, проверит доставку уведомлений,
подберёт рабочий режим браузера, зарегистрирует задачу в планировщике и
запустит монитор.

Режим браузера подбирается автоматически: сначала пробуется скрытый (он не
мозолит глаза), и только если Cloudflare его не пропускает — обычный, с окном
за пределами экрана. Выбор записывается в `.env`, чтобы не повторять подбор
при каждом запуске.

После этого монитор работает в фоне без окна консоли и стартует сам при входе
в систему.

| | |
|---|---|
| Логи | `monitor.log` |
| Настройки | `.env` (там же меняется интервал и всё остальное) |
| Убрать | `windows\uninstall.bat` |

### Что сделано для ноутбука, который засыпает

Настройки планировщика по умолчанию для такой задачи не годятся, поэтому
задача создаётся из XML с исправлениями:

* **Работа от батареи.** Windows по умолчанию не запускает задачи без зарядки
  и останавливает их при отключении. Обе настройки выключены.
* **Возврат после сна.** Кроме запуска при входе в систему есть повторяющийся
  триггер раз в 15 минут: если монитор почему-то не работает, он поднимется
  сам, не дожидаясь перезагрузки. Копии при этом не плодятся.
* **Перезапуск при сбое** — каждую минуту, до 999 раз.
* **Без ограничения времени работы** — иначе Windows убила бы задачу через трое суток.

**Важно понимать:** пока компьютер спит или выключен, проверок не происходит.
Талоны появляются в произвольное время, поэтому чем дольше машина в работе, тем
выше шанс поймать. Чтобы это было видно, при каждом запуске приходит сводка
(«Монитор запущен. Сейчас мест нет»), а суточное «сердцебиение» показывает
реальное число проверок за сутки — по нему видно, сколько слежка простаивала.

Если хочется, чтобы компьютер **сам просыпался** для проверок, установите с
ключом:

```
windows\setup.bat --wake
```

Тогда Windows будет будить машину по расписанию задачи. Настройка меняет
поведение питания, поэтому по умолчанию выключена.

### Если что-то не работает

```
.venv\Scripts\python.exe monitor.py --once     заглянуть на сайт один раз
.venv\Scripts\python.exe monitor.py --probe    проверить, пускает ли сайт
type monitor.log                               посмотреть логи
schtasks /Query /TN PassportQueueMonitor       состояние задачи
```

## Запуск локально

```bash
pip install -r requirements.txt

export TELEGRAM_BOT_TOKEN='<токен от BotFather>'
export TELEGRAM_CHAT_ID='<твой chat_id>'

python monitor.py
```

### Как узнать свой `TELEGRAM_CHAT_ID`

> **Сначала обязательно нажми `/start`.** Telegram не даёт боту написать первым
> тому, кто не открывал с ним чат. Пока `/start` не нажат, отправка падает с
> `Bad Request: chat not found` — даже если `TELEGRAM_CHAT_ID` абсолютно верный.
> Это самая частая причина «монитор работает, а уведомлений нет».

1. Открой в Telegram чат со своим ботом и отправь ему `/start`.
2. Выполни:

```bash
TELEGRAM_BOT_TOKEN='<токен>' python monitor.py --chat-id
```

Команда выведет готовую строку вида `TELEGRAM_CHAT_ID=123456789`.

При старте монитор сам проверяет доставку и пишет в лог
`Самопроверка Telegram пройдена`. Если не прошла — в логе будет строка
`ЧТО ДЕЛАТЬ:` с конкретной причиной. Монитор при этом не падает: он продолжит
следить за сайтом, и как только доставка починится, уведомления пойдут.

### Полезные команды

```bash
python monitor.py --once            # одна проверка, показать состояние и выйти
python monitor.py --test-telegram   # проверить, что уведомления доходят
python monitor.py --chat-id         # узнать chat_id
python monitor.py --simulate tests/fixtures/open.html    # прогнать парсер на файле
python monitor.py --simulate-open   # эмуляция «даты появились» с реальным уведомлением
python tests/test_parser.py         # тесты (или python -m pytest tests/ -v)
```

`--simulate-open` подменяет ответ сайта фикстурой с датами и проходит полный путь
до отправки сообщения в Telegram — это проверка критерия готовности №3 из ТЗ.

## Переменные окружения

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | — | **обязательна.** Токен от BotFather |
| `TELEGRAM_CHAT_ID` | — | **обязательна.** Куда слать |
| `INSTANCE_NAME` | определяется само | Подпись под сообщениями: чья это копия монитора |
| `FETCH_MODE` | `auto` | `direct` — прямой HTTP, `browser` — Playwright, `auto` — начать с direct и переключиться на браузер при блокировках |
| `SCRAPE_PROXY` | пусто | Один прокси: `http://user:pass@host:port` |
| `PROXY_LIST` | пусто | Список прокси через перевод строки/запятую. Приоритетнее `SCRAPE_PROXY` |
| `PROXY_LIST_PATH` | пусто | Путь к файлу со списком прокси (на Render — Secret File) |
| `PROXY_PRECHECK` | `true` | Отобрать рабочие прокси при старте |
| `PROXY_ROTATE_AFTER` | `3` | Ошибок подряд до переключения на следующий прокси |
| `PROXY_CHECK_TIMEOUT` | `20` | Таймаут проверки одного прокси, секунды |
| `PROXY_CACHE_HOURS` | `6` | Сколько часов доверять прошлой проверке, не повторяя её |
| `BROWSER_WIDTH` / `BROWSER_HEIGHT` | `1280` / `800` | Размер окна браузера. Меньше окно — меньше памяти |
| `INTERVAL_SECONDS` | `45` | Базовый интервал проверки. **Ниже 30 не опустится** — защита от бана |
| `JITTER_SECONDS` | `15` | Случайная добавка 0..N секунд |
| `BROWSER_INTERVAL_SECONDS` | `60` | То же для режима браузера |
| `BROWSER_JITTER_SECONDS` | `30` | Итого 60–90 секунд |
| `REQUEST_TIMEOUT` | `40` | Таймаут запроса, секунды |
| `CHALLENGE_WAIT_SECONDS` | `60` | Сколько браузер ждёт прохождения челленджа Cloudflare |
| `BROWSER_HEADLESS` | `true` | В Docker-образе принудительно `false`: headless Cloudflare часто не пропускает |
| `ERROR_THRESHOLD` | `5` | Сколько ошибок подряд до сообщения «забанили» |
| `ERROR_PAUSE_MINUTES` | `15` | Пауза после серии ошибок |
| `HEARTBEAT_HOUR` | `10` | Час суточного «сердцебиения» |
| `HEARTBEAT_TIMEZONE` | `Europe/Warsaw` | Часовой пояс для него |
| `STARTUP_NOTICE_COOLDOWN_MINUTES` | `60` | Не слать приветствие чаще, чем раз в столько минут |
| `STATE_PATH` | `state.json` | Где хранить состояние |
| `NOTIFY_ON_CLOSE` | `false` | Слать ли «места закончились» |
| `TARGET_URL` | страница варшавского центра | Можно навести на другой город |
| `LOG_LEVEL` | `INFO` | `DEBUG` покажет тайминги сна |
| `LOG_FILE` | пусто | Дублировать логи в файл. Нужно при фоновом запуске без консоли |

Переменные можно не задавать вручную: если рядом с `monitor.py` лежит файл
`.env` вида `KEY=VALUE`, монитор прочитает его при старте. Настоящие переменные
окружения всегда важнее файла, так что на Render и в systemd ничего не меняется.

### Как поменять интервал

`INTERVAL_SECONDS` и `JITTER_SECONDS` — фактический интервал равен
`INTERVAL_SECONDS + случайные 0..JITTER_SECONDS`. По умолчанию 45–60 секунд.

Значения ниже 30 секунд принудительно поднимаются до 30 (`MIN_INTERVAL_SECONDS`
в `config.py`) — чаще ходить нельзя, это прямой путь к бану IP.

### Про cookies

Их нет и перевыпускать нечего — см. раздел «Разведка», пункт 2. Если сайт когда-нибудь
начнёт их требовать, признак будет такой: в ответе появится `set-cookie`, а без него
пойдут редиректы или 403 с HTML-страницей (а не с текстом `Blocked for security
reasons`). Тогда нужно будет либо перейти на `FETCH_MODE=browser` (Playwright держит
cookies сам), либо добавить их в `browser_headers()` в `fetcher.py`.

## Деплой на Render

Тип сервиса — **Background Worker** (не Web Service: входящий HTTP не нужен).
Собирается Docker-образ на базе официального Playwright-образа с Chromium:
без браузера челлендж Cloudflare не пройти, а без прохождения челленджа сайт
недоступен (см. «Если Cloudflare блокирует»).

1. Запушить репозиторий на GitHub.
2. В Render: **New → Blueprint**, указать этот репозиторий. Подхватится `render.yaml`.
3. Заполнить переменные с `sync: false`: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`
   и `PROXY_LIST`.
4. Задеплоить и проверить логи — там должно быть `Состояние очереди: closed`.

> Если сервис уже создан с Python-рантаймом, смена `runtime` в `render.yaml`
> сама по себе не переключит его. Проще пересоздать сервис из Blueprint —
> переменные окружения при этом надо будет ввести заново.

### Память

Настоящий Chromium — самая тяжёлая часть, и на тарифе с 512 МБ контейнер
убивал процесс прямо посреди прохождения челленджа: в логах не было исключения,
просто «Instance restarted». Поэтому расход печатается на ключевых шагах:

```
monitor: Память (старт): 90 МБ из 512 МБ (18%)
monitor: Память (после проверки прокси): 130 МБ из 512 МБ (25%)
fetcher: Память (браузер с челленджем): 400 МБ из 512 МБ (78%)
```

При расходе выше 85% в лог идёт отдельное предупреждение. Если убийства
продолжаются, помогут:

* уменьшить окно браузера — `BROWSER_WIDTH=1024`, `BROWSER_HEIGHT=768`;
* вернуться к прямым запросам, если найдётся прокси без челленджа;
* взять тариф с большим объёмом памяти.

Результат проверки прокси кэшируется в `state.json` на `PROXY_CACHE_HOURS`
часов: при частых перезапусках не нужно каждый раз тратить полторы минуты и
память на все 160 адресов. В файл пишутся не адреса, а их номера в списке —
учётным данным там не место.

Первый запуск в режиме браузера дольше обычного: сначала проверка прокси
(около минуты), потом прохождение челленджа (до 60 секунд). В логах это видно:

```
monitor: Итог проверки: пропускают сразу — 0, отдают челлендж — 50, забанены — 110
monitor: Годных прокси: 50. Использую http://arqFSv@168.81.66.60:8000
fetcher: Cloudflare показал челлендж, жду прохождения...
fetcher: Челлендж пройден за 6 сек
monitor: Состояние очереди: closed
```

Регион в `render.yaml` — `frankfurt` (ближайший к Варшаве). Логи пишутся в stdout,
Render собирает их сам.

Диск на 1 ГБ примонтирован в `/var/data`, чтобы `state.json` переживал передеплой.
Без диска ничего страшного не случится: после рестарта максимум придёт одно
повторное уведомление. Если хочется сэкономить — удалите блок `disk` и
переменную `STATE_PATH`.

### Если браузер не нужен

Когда найдётся прокси или хостинг, с которого сайт пускает без челленджа
(`--probe` показывает `OK, САЙТ ПУСКАЕТ`), можно вернуться на лёгкий
Python-рантайм: он собирается втрое быстрее и ест меньше памяти.

```yaml
    runtime: python
    buildCommand: pip install -r requirements.txt
    startCommand: python monitor.py
```

и `FETCH_MODE=direct`.

## Если Cloudflare блокирует

Симптом: в Telegram приходит «⚠️ Похоже, забанили», в логах —
`Cloudflare заблокировал IP (правило WAF «Blocked for security reasons»)`.

Ключевое: Cloudflare отвечает **двумя разными способами**, и путать их нельзя.

| Ответ | Что это | Проходится браузером? |
|---|---|---|
| `403 Blocked for security reasons`, без `cf-mitigated` | жёсткое правило WAF по IP/ASN | **нет**, помогает только смена IP |
| Страница `Just a moment…` / `cdn-cgi/challenge-platform` | обычный JS-челлендж | **да**, настоящий браузер решает его сам за несколько секунд |

Поэтому монитор различает их в логах: `IP ЗАБЛОКИРОВАН` против `ЧЕЛЛЕНДЖ/КАПЧА`.
Первое — приговор для этого IP, второе — штатная ситуация для Варианта Б.

### Что уже измерено

**Render без прокси не подошёл** — с его IP сайт отдаёт жёсткий 403:

```
monitor: Ошибка проверки (1 подряд): HTTP 403: Cloudflare заблокировал IP
```

Блокировка накрывает всю зону: 403 приходит на `pasport.org.ua`,
`warszawa.pasport.org.ua`, `krakow.pasport.org.ua` и даже на статику вроде
`/sw.js`. Обходного хоста нет. Заблокированы и два разных дата-центра в разных
странах (США и Германия) — режут по ASN дата-центров, а не по стране, так что
дешёвый VPS может оказаться забанен ровно так же.

**А вот через прокси картина другая.** Проверка списка из 160 адресов дала
чёткое разделение:

```
http://…@45.91.209.129:11109      IP ЗАБЛОКИРОВАН     (110 адресов, 1 IP)
http://…@168.81.66.60:8000        ЧЕЛЛЕНДЖ/КАПЧА      (~50 адресов, 11 IP)
```

Челлендж — не бан. Именно ради него в ТЗ и был предусмотрен Вариант Б.
Поэтому рабочая конфигурация — **браузер + прокси, отдающие челлендж**:
Playwright проходит проверку, полученная кука `cf_clearance` живёт в контексте
браузера, и последующие проверки идут уже без задержки.

### Почему браузер запускается не в headless

Первая попытка в headless-режиме челлендж не прошла: страница провисела
45 секунд и осталась на месте, хотя `playwright-stealth` был подключён.
Cloudflare умеет отличать headless-Chromium по набору признаков, которые
маскировка не закрывает.

Поэтому в Docker-образе поднимается виртуальный дисплей Xvfb, и Chromium
работает как настоящий (`BROWSER_HEADLESS=false`). Xvfb входит в официальный
образ Playwright, ставить ничего не нужно.

Дисплей поднимает `display.py` прямо перед запуском браузера, а не скрипт при
старте контейнера. Причина практическая: между стартом и первым запуском
браузера проходит около минуты (проверка прокси), и Xvfb может до него не
дожить — тогда браузер падает с `Missing X server or $DISPLAY`. Здесь дисплей
проверяется на живость перед каждым запуском и при необходимости поднимается
заново, а если Xvfb недоступен вовсе — монитор переходит в headless и пишет
предупреждение, но не падает. Побочный плюс: `python` остаётся главным
процессом контейнера и штатно обрабатывает `SIGTERM` от Render.

Если челлендж всё равно не пройден, в логах печатается диагностика: заголовок
страницы, её текст и число iframe'ов Turnstile. По ним видно, ждёт ли проверка
клика (тогда монитор пробует нажать чекбокс сам) или упирается во что-то ещё.
На боевых логах она показала «Трохи зачекайте… Триває перевірка безпеки» при
нуле iframe'ов — то есть самопроходящий JS-челлендж без капчи, ровно тот тип,
который решается настоящим браузером.

Важная тонкость: дисплей поднимается **до** `sync_playwright().start()`.
Драйвер Playwright — отдельный процесс, он наследует окружение в момент
запуска и передаёт его браузеру. Если выставить `DISPLAY` после старта
драйвера, Chromium его не увидит и упадёт с «without having a XServer
running», а откат на headless это тихо замаскирует. Для надёжности окружение
дополнительно передаётся в `launch(env=...)` явно.

### Как проверить кандидата, ничего не покупая

```bash
python monitor.py --probe                          # с текущего IP
SCRAPE_PROXY=http://user:pass@host:port python monitor.py --probe   # через прокси
```

Команда печатает код ответа, вердикт и `cf-ray` (по суффиксу видно дата-центр
Cloudflare) и возвращает 0, если IP годится. Запускать **до** оплаты хостинга —
у большинства провайдеров прокси есть триал, а VPS почти везде можно взять на
час.

### Варианты, по убыванию надёжности

1. **Прокси + Render** — если список прокси уже есть, это самый быстрый путь.
   См. следующий раздел.
2. **Своя машина дома.** Бесплатно и надёжно: домашний IP уже доказал, что сайт
   с него открывается — именно оттуда снимался HAR. Подойдёт Raspberry Pi,
   старый ноутбук, NAS. См. раздел «Запуск дома под systemd».
3. **VPS в Польше** (`mikr.us`, OVH Варшава, Hetzner). Дёшево, но, судя по
   измерениям выше, риск получить те же 403 реальный. Брать только после
   проверки `--probe` с триального или почасового инстанса.

## Работа со списком прокси

Прокси — расходник: часть адресов мертва, часть забанена сайтом, и со временем
это меняется. Поэтому монитор умеет работать не с одним адресом, а со списком:
сам выбирает рабочий и переключается, когда текущий отваливается.

Список задаётся одним из двух способов:

* `PROXY_LIST` — прямо в переменной окружения, адреса через перевод строки или
  запятую. Удобно для Render: вставляется в поле значения как есть.
* `PROXY_LIST_PATH` — путь к файлу. На Render это **Secret File**
  (Environment → Secret Files), примонтированный, например, в `/etc/secrets/proxies.txt`.

Понимаются форматы (по одному на строку, `#` — комментарий):

```
168.81.66.60:8000:user:pass      # формат выгрузок большинства провайдеров
168.81.66.60:8000
http://user:pass@168.81.66.60:8000
socks5://user:pass@168.81.66.60:1080
```

Пароли в логи не попадают — адреса печатаются замаскированными.

### Сначала отобрать рабочие

```bash
PROXY_LIST_PATH=proxies.txt python monitor.py --probe-list
```

Проверяет весь список параллельно (20 потоков) и печатает те адреса, через
которые сайт реально пускает. Запускать нужно **оттуда, где будет крутиться
монитор** — годность прокси не зависит от того, откуда вы к нему подключаетесь,
а вот доступность порта зависит.

### Как это работает в бою

* **При старте** монитор прогоняет весь список и оставляет годные
  (`PROXY_PRECHECK=true` по умолчанию). Проверить 160 адресов — примерно минута,
  зато дальше цикл не спотыкается о мёртвые. Что считается годным, зависит от
  режима: при `FETCH_MODE=direct` — только те, что пускают сразу; при
  `browser`/`auto` — ещё и отдающие челлендж, потому что браузер его проходит.
  Адреса без челленджа при этом идут первыми.
* **В работе**, если текущий прокси даёт `PROXY_ROTATE_AFTER` ошибок подряд
  (по умолчанию 3), монитор молча берёт следующий — без долгой паузы, потому что
  дело почти наверняка в конкретном адресе, а не в сайте.
* **Только когда перебран весь пул** и ничего не сработало, приходит «⚠️ Похоже,
  забанили» и включается пауза на 15 минут. Так одно сообщение соответствует
  реальной проблеме, а не смерти одного прокси из ста шестидесяти.

Если прокси не нужны, ничего задавать не надо: пустой список означает прямое
подключение, и всё работает как раньше.

## Запуск дома под systemd

Для варианта «своя машина» Render не нужен вообще:

```bash
git clone <репозиторий> && cd pasport
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python monitor.py --probe     # убедиться, что IP годится
```

Юнит `/etc/systemd/system/passport-monitor.service`:

```ini
[Unit]
Description=Монитор очереди паспортного сервиса
After=network-online.target

[Service]
Type=simple
WorkingDirectory=/opt/pasport
Environment=TELEGRAM_BOT_TOKEN=...
Environment=TELEGRAM_CHAT_ID=...
Environment=FETCH_MODE=direct
ExecStart=/opt/pasport/.venv/bin/python monitor.py
Restart=always
RestartSec=30

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable --now passport-monitor
journalctl -u passport-monitor -f
```

Монитор корректно обрабатывает SIGTERM, так что `systemctl restart` и
`systemctl stop` отрабатывают чисто, без убийства процесса по таймауту.
