# Монитор электронной очереди — паспортный сервис, Варшава

Следит за страницей [warszawa.pasport.org.ua/solutions/e-queue](https://warszawa.pasport.org.ua/solutions/e-queue)
и присылает в Telegram сообщение, как только появляются свободные даты для записи.

Записываться сам **не умеет и не будет** — только уведомляет. Запись руками.

---

## Разведка: что выяснилось из HAR

Это результат Этапа 0 из ТЗ. Читать обязательно — от этого зависит, почему код
устроен именно так.

### 1. Отдельного API со списком дат нет

В HAR-файле (60 запросов) **нет ни одного XHR/fetch с JSON-ответом** про даты или
слоты. Все запросы к домену — это сама страница, JS-чанки, шрифты, иконки и
телеметрия (Google Analytics, Cloudflare RUM).

Состояние очереди приходит **уже отрисованным в HTML** самой страницы. Когда мест
нет, в левой колонке лежит серверный блок:

```html
<div class="... border-red-500 bg-red-50 text-red-600" role="alert">
  <p><strong>Наразі всі місця зайняті.</strong></p>
  <p>Будь ласка, спробуйте в інший час або день.</p>
  <p>Кількість талонів обмежена пропускною здатністю центру.</p>
</div>
```

Это хорошая новость: чтобы узнать состояние, достаточно скачать одну HTML-страницу.
Никаких токенов, id услуги и офиса, тел запроса — ничего этого нет.

Виджет записи (выбор услуги, даты, верификация через Дію/BankID) — это ленивые
webpack-чанки `app.m-queue-*.js`, которые подгружаются только когда талоны есть.
На момент экспорта HAR мест не было, поэтому **разметку «открытого» состояния снять
не удалось**. Как парсер это компенсирует — ниже.

### 2. Cookies не нужны

У запроса страницы в HAR **нет заголовка `cookie` вообще**. Сессия не нужна,
CSRF-токенов нет, ничего не «протухает». Пункт ТЗ про перевыпуск cookies
неприменим — перевыпускать нечего.

### 3. Cloudflare блокирует по IP, а не по «роботности»

Ключевой момент. Проверено с датацентрового IP:

| Запрос | Результат |
|---|---|
| `curl` без заголовков | `403 Blocked for security reasons` (28 байт) |
| `curl` с полным набором браузерных заголовков из HAR | тот же `403` |
| TLS-отпечаток Safari (curl_cffi) | тот же `403` |
| Ваш браузер (`cf-ray: ...-PRG`, Прага) | `200 OK` |
| Тестовая машина (`cf-ray: ...-IAD`, датацентр США) | `403` |

В ответе **нет заголовка `cf-mitigated`** и нет HTML с JS-челленджем — значит это
не «Managed Challenge», который решается браузером, а **кастомное WAF-правило,
режущее по IP/ASN**.

Практический вывод, важный для деплоя:

> **Headless-браузер сам по себе эту блокировку не обходит.** Вариант Б из ТЗ
> помогает против JS-челленджей, а здесь блок другого рода. Решает не браузер,
> а «чистый» IP-адрес.

Поэтому в коде есть `SCRAPE_PROXY` — единственная настройка, которая реально
чинит ситуацию, если IP хостинга забанен. См. раздел
[«Если Cloudflare блокирует»](#если-cloudflare-блокирует).

## Как устроено

```
monitor.py     — основной цикл, логика уведомлений, CLI
fetcher.py     — загрузка страницы: прямой HTTP (Вариант А) или Playwright (Вариант Б)
parser.py      — разбор HTML в состояние очереди
notifier.py    — Telegram
state.py       — сохранение состояния между проверками
config.py      — все настройки из переменных окружения
tests/         — тесты парсера + фикстуры реальной страницы
```

### Логика парсера

Разметку «даты есть» вживую снять не удалось, поэтому парсер намеренно
консервативен и различает **три** состояния, а не два:

| Что нашли на странице | Состояние | Действие |
|---|---|---|
| Маркер «Наразі всі місця зайняті» | `closed` | молчим |
| Маркера нет, есть виджет записи и/или даты | `open` | **шлём уведомление** |
| Ни того, ни другого | `unknown` | молчим, пишем в лог |

Так изменение вёрстки приведёт к «промолчали», а не к ложной тревоге в три часа
ночи. Если `unknown` держится ~час подряд (60 проверок), придёт отдельное
сообщение «возможно, изменилась вёрстка» — чтобы молчание не осталось незамеченным.

Даты извлекаются в форматах `12.08.2026`, `2026-08-12`, `03.11` и `14 серпня`,
приводятся к `ДД.ММ` и отдаются в порядке появления на странице.

### Когда приходят уведомления

* **🚀 Монитор запущен** — один раз при старте, это же и самопроверка доставки.
  Беззвучно.
* **🟢 Появились даты** — при появлении дат, которых раньше не было, или при
  переходе очереди из закрытой в открытую. Со звуком.
  Повторно теми же датами не спамит.
* **✅ Сердцебиение** — раз в сутки в 10:00 (Europe/Warsaw): сколько было проверок
  и ошибок за сутки. Беззвучно.
* **⚠️ Забанили / сайт лёг** — после 5 ошибок подряд, затем пауза 15 минут.
  Присылается один раз за «эпизод», не на каждой пятой ошибке.
* **✅ Связь восстановилась** — когда сайт снова отвечает. Беззвучно.
* **🔴 Места закончились** — выключено по умолчанию, включается `NOTIFY_ON_CLOSE=true`.

## Запуск локально

```bash
pip install -r requirements.txt

export TELEGRAM_BOT_TOKEN='<токен от BotFather>'
export TELEGRAM_CHAT_ID='<твой chat_id>'

python monitor.py
```

### Как узнать свой `TELEGRAM_CHAT_ID`

> **Сначала обязательно нажми `/start`.** Telegram не даёт боту написать первым
> тому, кто не открывал с ним чат. Пока `/start` не нажат, отправка падает с
> `Bad Request: chat not found` — даже если `TELEGRAM_CHAT_ID` абсолютно верный.
> Это самая частая причина «монитор работает, а уведомлений нет».

1. Открой в Telegram чат со своим ботом и отправь ему `/start`.
2. Выполни:

```bash
TELEGRAM_BOT_TOKEN='<токен>' python monitor.py --chat-id
```

Команда выведет готовую строку вида `TELEGRAM_CHAT_ID=123456789`.

При старте монитор сам проверяет доставку и пишет в лог
`Самопроверка Telegram пройдена`. Если не прошла — в логе будет строка
`ЧТО ДЕЛАТЬ:` с конкретной причиной. Монитор при этом не падает: он продолжит
следить за сайтом, и как только доставка починится, уведомления пойдут.

### Полезные команды

```bash
python monitor.py --once            # одна проверка, показать состояние и выйти
python monitor.py --test-telegram   # проверить, что уведомления доходят
python monitor.py --chat-id         # узнать chat_id
python monitor.py --simulate tests/fixtures/open.html    # прогнать парсер на файле
python monitor.py --simulate-open   # эмуляция «даты появились» с реальным уведомлением
python tests/test_parser.py         # тесты (или python -m pytest tests/ -v)
```

`--simulate-open` подменяет ответ сайта фикстурой с датами и проходит полный путь
до отправки сообщения в Telegram — это проверка критерия готовности №3 из ТЗ.

## Переменные окружения

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | — | **обязательна.** Токен от BotFather |
| `TELEGRAM_CHAT_ID` | — | **обязательна.** Куда слать |
| `FETCH_MODE` | `auto` | `direct` — прямой HTTP, `browser` — Playwright, `auto` — начать с direct и переключиться на браузер при блокировках |
| `SCRAPE_PROXY` | пусто | Прокси для запросов: `http://user:pass@host:port` |
| `INTERVAL_SECONDS` | `45` | Базовый интервал проверки. **Ниже 30 не опустится** — защита от бана |
| `JITTER_SECONDS` | `15` | Случайная добавка 0..N секунд |
| `BROWSER_INTERVAL_SECONDS` | `60` | То же для режима браузера |
| `BROWSER_JITTER_SECONDS` | `30` | Итого 60–90 секунд |
| `REQUEST_TIMEOUT` | `40` | Таймаут запроса, секунды |
| `ERROR_THRESHOLD` | `5` | Сколько ошибок подряд до сообщения «забанили» |
| `ERROR_PAUSE_MINUTES` | `15` | Пауза после серии ошибок |
| `HEARTBEAT_HOUR` | `10` | Час суточного «сердцебиения» |
| `HEARTBEAT_TIMEZONE` | `Europe/Warsaw` | Часовой пояс для него |
| `STATE_PATH` | `state.json` | Где хранить состояние |
| `NOTIFY_ON_CLOSE` | `false` | Слать ли «места закончились» |
| `TARGET_URL` | страница варшавского центра | Можно навести на другой город |
| `LOG_LEVEL` | `INFO` | `DEBUG` покажет тайминги сна |

### Как поменять интервал

`INTERVAL_SECONDS` и `JITTER_SECONDS` — фактический интервал равен
`INTERVAL_SECONDS + случайные 0..JITTER_SECONDS`. По умолчанию 45–60 секунд.

Значения ниже 30 секунд принудительно поднимаются до 30 (`MIN_INTERVAL_SECONDS`
в `config.py`) — чаще ходить нельзя, это прямой путь к бану IP.

### Про cookies

Их нет и перевыпускать нечего — см. раздел «Разведка», пункт 2. Если сайт когда-нибудь
начнёт их требовать, признак будет такой: в ответе появится `set-cookie`, а без него
пойдут редиректы или 403 с HTML-страницей (а не с текстом `Blocked for security
reasons`). Тогда нужно будет либо перейти на `FETCH_MODE=browser` (Playwright держит
cookies сам), либо добавить их в `browser_headers()` в `fetcher.py`.

## Деплой на Render

Тип сервиса — **Background Worker** (не Web Service: входящий HTTP не нужен).

1. Запушить репозиторий на GitHub.
2. В Render: **New → Blueprint**, указать этот репозиторий. Подхватится `render.yaml`.
3. В настройках сервиса заполнить переменные с `sync: false`:
   `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, при необходимости `SCRAPE_PROXY`.
4. Задеплоить и проверить логи — там должно быть `Состояние очереди: closed`.

Регион в `render.yaml` — `frankfurt` (ближайший к Варшаве). Логи пишутся в stdout,
Render собирает их сам.

Диск на 1 ГБ примонтирован в `/var/data`, чтобы `state.json` переживал передеплой.
Без диска ничего страшного не случится: после рестарта максимум придёт одно
повторное уведомление. Если хочется сэкономить — удалите блок `disk` и
переменную `STATE_PATH`.

### Переключение на браузер на Render

В `render.yaml` заменить:

```yaml
    runtime: python
    buildCommand: pip install -r requirements.txt
    startCommand: python monitor.py
```

на:

```yaml
    runtime: docker
    dockerfilePath: ./Dockerfile
```

и поставить `FETCH_MODE=browser`. Соберётся образ на базе официального
Playwright-образа с Chromium. Но сначала прочитайте следующий раздел — скорее
всего, это не то, что нужно.

## Если Cloudflare блокирует

Симптом: в Telegram приходит «⚠️ Похоже, забанили», в логах —
`Cloudflare заблокировал IP (правило WAF «Blocked for security reasons»)`.

**Важно: переключение на браузер здесь, скорее всего, не поможет.** Как показано
в разделе «Разведка», это блокировка по IP/ASN, а не JS-челлендж. Браузер решает
челленджи, но не меняет IP.

Порядок действий, от дешёвого к дорогому:

1. **Сначала просто задеплоить на Render и посмотреть.** Диапазоны Render могут
   быть не в блок-листе — тогда всё работает и делать ничего не нужно. Ничего
   не покупайте заранее.
2. **Если 403 — прокси.** Задать `SCRAPE_PROXY=http://user:pass@host:port`.
   Работает и с прямыми запросами, и с браузером. Нужен польский/европейский
   резидентный прокси; датацентровый, скорее всего, забанен так же.
3. **Если и это не подошло — свой VPS в Польше.** `mikr.us`, OVH Варшава,
   Hetzner. Несколько евро в месяц, IP локальный. Запуск там —
   `pip install -r requirements.txt && python monitor.py` под systemd или
   в Docker; Render в этом случае не нужен вообще.

Проверить, блокирует ли конкретный IP, можно за секунду:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://warszawa.pasport.org.ua/solutions/e-queue
# 200 — всё хорошо, 403 — IP забанен
```

## Чего монитор не делает

* Не записывается на дату автоматически — только уведомляет.
* Не ходит на сайт чаще раза в 30 секунд.
* Не хранит токены в коде — только в переменных окружения.
